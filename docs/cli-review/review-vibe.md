# Cross-model review: docs/cli-review/CLI-REVIEW.md (proposal only, no files touched)

Overall: the proposal is well-aligned with the guideline and the findings are real (I verified them against the inlined `registerOptionsAndFlags_`, `instrumentClass` and the helphelp dump). But it contains two critical defects — an internal contradiction in the release timeline, and a silent results change for every non-Astral Orbitrap and non-tims TOF — plus a handful of unspecified mechanisms that will bite in implementation.

## 1. Compatibility plan

**A1 — Critical: the alias window contradicts decision 7.** The compatibility section says aliases live "for one minor release, until 0.3", and the deprecation text says "removed in 0.3". Decision 7 ships this cleanup *as* 0.3.0, with 0.2.16 carrying only the post-V0.2.15 work (physical cores, 7-sigma window, decoy population, .pkg). So aliases would be introduced and removed in the same release — zero releases of compatibility. Failing case: a user on a 0.2.14 INI upgrades to the recommended 0.2.16 and still gets exit 6, because the fix is deferred to the release in which it also dies. Either fold the aliases into 0.2.16 (my recommendation) or extend removal to 0.4. Also acknowledge explicitly that 0.2.15 already broke the guideline's "one minor release" promise — the alias period is remediation, not fresh grace.

**A2 — High: value-level migrations are listed as if option-aliasing covered them.** Three of the "renames" are on the *same option name* or a sentinel value, which hidden-advanced alias registration does not touch:
- `-rt_mode` still exists, but its valid set shrank (old: `auto|minutes|seconds|identity|anchors|trafo|linear`; new per `setValidStrings_` line 21: `auto|minutes|seconds`). TOPPBase rejects an INI carrying `rt_mode: anchors` as an invalid string *before* any alias layer runs. The friendly "anchors → implied by the file" message needs its own INI/CLI migration path.
- `-ms1_isotopes -1` → `-no_ms1`: `-ms1_isotopes` still exists with `setMinInt 0` (line 47), so `-ms1_isotopes -1` dies in the range check. The sentinel must be intercepted before validation.

**A3 — High: silent results changes are outside the compatibility section entirely.** The compatibility plan covers *names* only. Since the 0.2.15 tag, the RT window rule (729c57c: 7 sigma + 2 FWHM), the calibration decoy population (cbae00b) and the threads default changed. An old INI with `rt_window: 0` and no explicit tolerances produces different Parquet bytes in 0.2.16 with no warning. The guideline's changed-defaults table keyed on the INI's recorded version (section 3.4) is absent from the proposal. The identity test "old full command vs new short command" is also ambiguous: identical to *current main* is achievable; identical to 0.2.14 is not (the RT window and calibration semantics changed). State which, and whitelist the intended provenance-key diffs (`odia.instrument*`) explicitly.

**A4 — Medium: the combination equivalence can map a working old command onto a hard error.** `-aggregation sum -ms1_isotope_spacing unit -mz_calibration off` → `-scheme B`, but scheme B "needs -mz_tol_ms2 and -mz_tol_ms1" (help, lines 30-33). Old command with *measured* tolerances under those flags worked; mapped to scheme B it now errors. Partial matches (only one of the trio) need a defined message. And the "removed at old default → WARNING, else error" rule needs the table of old defaults written out in the review doc, or it will be guessed at implementation time.

**A5 — Medium: "-write_ini writes only the new names" has no mechanism.** TOPPBase's `writeIni` writes every registered parameter; registering `mz_tol` as a hidden alias makes it appear in fresh INIs and in `-write_ctd`/`-write_cwl` output (Galaxy/KNIME would show deprecated names). This needs a skip-by-name list in the patched OpenMS (the guideline's "name list, not the advanced flag" rule), and the proposal should say so.

**A6 — Low:** the inventory covers the *current* names only. The ~30 old names' uses in docs, scripts and archived benchmarks are not enumerated; the guideline requires archived scripts to keep working through the aliases. Also: state plainly whether a GUI exists (if none, say so — the guideline item is then void).

## 2. Instrument data files

**B1 — Critical: recommended decision 3 silently regresses every non-Astral Orbitrap and every non-tims TOF.** Today `instrumentClass` (DIATraceExtractor.cpp:113-114) gives 9 sigma to the whole Orbitrap family (Exploris, Exactive, Lumos, Fusion, Eclipse, Velos, Elite, Tribrid, Ascend) and 4 to anything matching "tof" (Waters, SCIEX TripleTOF). Under the recommendation ("other Orbitraps and TOFs fall back to the generic 6"), those drop to 6 with no file, no warning, no CHANGELOG entry. Failing case: an Exploris 480 run, no `-instrument`, no explicit tolerance → 0.2.15: 9 sigma; 0.2.16: 6 sigma → narrower fragment tolerance, fewer edge peaks, different bytes, silence. This violates guideline section 0 ("no silent behaviour") and is not "don't invent values" either — 6 for an Exploris is exactly as unsourced as 9. Note also the observable delta of the recommendation is *purely negative*: the two shipped files state 9 and 4, i.e. exactly what the class rule already gives Astral and timsTOF. The files' value is extensibility and provenance, which survives intact if the class rule stays as the fallback for unmatched strings.

**B2 — High: the metadata-string → file matching algorithm is unspecified.** The guideline (2.2 and the pitfalls) prescribes normalize case/space/`-`/`_`/vendor prefix/trailing model number "and nothing more"; `instrumentClass` today is loose substring `has()`. The proposal says nothing about how `"Thermo Scientific Q Exactive HF"` or `"timsTOF Ultra"` resolves against `name`/`aliases`. Failing cases: "timsTOF Ultra" not in the alias list → falls through (was 4 under `has("tims")`); multi-token strings colliding with several files need a defined precedence; an over-loose matcher re-creates the "Exploris matches Exploris 480" pitfall in reverse.

**B3 — Medium: provenance vs fingerprint.** The guideline says file names/hashes are recorded but kept *out of the output fingerprint* ("the same values give the same output, whichever file supplied them"). The proposal adds `odia.instrument_files` (names and hashes) to the footer without saying whether it enters the fingerprint. Failing case: a user overrides `astral.yaml` with identical values → fingerprint changes → identity checks and any downstream caching break. Also: first-file-wins means a user's replacement `default.yaml` must be *complete* — specify whether strict validation errors on missing required keys.

**B4 — Medium / over-engineering for 0.2.x:** yaml-cpp from vcpkg into the patched OpenMS manifest, packaging on five platforms, licence-bundle notice — for two files whose entire per-instrument payload is *one scalar* (`mz_accuracy_ms2`; the MS1 multiple is constant and the RT window is deliberately not per instrument, decision 4). The guideline mandates an established parser, not yaml-cpp specifically; OpenMS's own Param/XML parser is established, already in the tree, and reads hand-editable XML. Similarly `$DIATRACEEXTRACTOR_INSTRUMENT_DIR` + user config dir + `-instrument_file` each carry search-path logging and their own test battery (guideline 2.3/6) with no demonstrated demand. Phasing is reasonable: ship files + `-instrument` now; defer the env var, user dir and single-file option until asked for.

**B5 — Low:** schema details unpinned: value ranges in files (`mz_accuracy_ms2` > 0?), whether yaml-cpp actually rejects duplicate map keys (test it — some builds silently take the last), alias case handling. The two shipped values are properly sourced ("report section 5") — good, that satisfies the guideline; the *fallback* values are the unsourced ones (see B1).

## 3. `-instrument` in basic help

**C1 — Low severity, but fix the text.** Basic is right: guideline section 0 makes naming the instrument a primary input, and it is the remedy for finding 3. Two problems: the help line hardcodes "(Astral 9, timsTOF 4, others 6)" — values that live in data files and a fallback rule that is decision 3, still open; the line is wrong the day the owner picks the alternative or a user adds a file. Write it as "a name from the instrument files (e.g. Astral, timsTOF); the resolved multiples are logged". Separately, the target help block lists **14** tool options, but the heading claims 17 (+3 TOPP). Under budget either way, but the guideline pins the line count by test — the written-out help must be complete and the count must match it.

## 4. Unknown-option pre-parse in main()

**D1 — High: a naive pre-parse breaks documented valid input.** `-rt_window` accepts negative values ("Negative: the whole run", registration line 22-24). A pre-parse that treats every `-`-prefixed token as an option name reports `Unknown option '-1'` and exits on a documented command. To do it right, the pre-parser must know which options take values (consume the next token) and which are flags — `-no_ms1 -out t.parquet` must not swallow `-out` as `no_ms1`'s value. That means duplicating TOPPBase's entire parse table in the tool, including `--threads` variants (already duplicated at lines 92-96 — the hazard exists today), `--help/--helphelp`, and whatever `-opt=value` support TOPPBase has (verify against the binary; the proposal verified the *bug* but not the *fix*).

**D2 — Medium, recommendation:** the tool already vendors a patched OpenMS (the boost-json precedent the proposal itself cites). The one-line "did you mean" message plus suppression of the usage dump belongs in `TOPPBase::parse_argv` — one mechanism, correct by construction, exit 6 preserved, and it also covers the INI path ("Unknown (or deprecated) Parameter 'mz_tol'... did you mean mz_tol_ms2?"), which a main() pre-parse cannot reach. A second parser next to the framework's is exactly the "don't invent a second mechanism" trap; if the pre-parse is kept anyway, its rules (value consumption, flag list, `--` variants) must be specified and tested against `-rt_window -1`, flags, `--help`, and `-ini`.

## 5. Diagnostics behind -debug 1

**E1 — Low severity, three gaps.** The direction is correct per guideline section 4 and the one-line-per-topic default level is the right shape. Missing:
- The consumer inventory is incomplete. The inventory TSV shows `debug` with uses_CI: 1 and several options with uses_tests > 0 (`mz_offset_ms1`: 7); grep the tests and CI *and* the benchmark scripts for `Calibration:`, `Scheduler:`, `Instrument:` before moving them, in the same commit. Decision 6 names only the benchmark scripts.
- The before/after message table (`docs/messages-review.md`, guideline section 4) is absent from the proposal.
- The replacement one-line calibration summary must carry the numbers consumers actually parse (anchors, offsets, widths) — confirm against the scripts; archived scripts gaining `-debug 1` means they are edited, which is fine for "keep working" but should be said.

## 6. Guideline items the proposal ignores

- **F1 — Medium, inert combinations (3.3):** finding 8 claims combination validation is "fine as is", but the inert cases are unhandled: `-mz_offset_ms2/_ms1` without `-mz_calibration off` (lines 59-63) are silently unused; `-rt_trafo_invert` without `-rt_trafo`; `-ms1_isotopes > 0` with `-no_ms1`; `-rt_mode minutes` together with `-rt_anchors` (help says the file "selects a given map instead" — precedence undefined, no warning). The guideline: warn in the minor release, error in the next.
- **F2 — Medium:** `docs/messages-review.md` (see E1).
- **F3 — Low, implied values in help (2.3):** finding 7 flags it, but the target help for `-mz_tol_ms2` still doesn't name the per-instrument multiple; the `-instrument` line does — cross-reference or accept explicitly.
- **F4 — Low:** CHANGELOG and doc updates (usage, parameters, "adding an instrument") appear nowhere in the phase-2 plan (checklist section 7).
- **F5 — Low:** no replay check that the footer + `-out_stats` values reproduce a run (the local equivalent of "-write_config replays the run exactly"), and no statement about a GUI.

## What is fine

The inventory and before-dumps (guideline 1.1) are done properly. The threads default, the TOPP-native basic/advanced split, the option descriptions, mode inference and output handling (finding 8) are all correct — leave them. Per-value precedence, the conflict error (old+new names), LF via `.gitattributes`, provenance-with-sources (modulo B3), the `WARNING:` prefix, once-per-run warnings, and the decision-list-with-recommendations format all match the guideline. Decision 4 (RT window in `default.yaml`, not per instrument) is right — just cite the source of 7 sigma + 2 FWHM in the file comment per the every-value-cites-its-source rule.

## Recommendations for the 7 owner decisions

| # | Decision | Recommendation |
|---|---|---|
| 1 | Aliases for 0.2.14 names | **Yes, but in 0.2.16, not 0.3.0** (A1). Add the value-level migrations (`rt_mode` old values, `ms1_isotopes -1`) and a changed-defaults note for INI-recorded versions; write out the old-defaults table before accepting removed options at defaults (A2-A4). |
| 2 | YAML files + `-instrument` + yaml-cpp | **Yes to files and `-instrument`.** Weigh yaml-cpp-from-vcpkg (five platforms, packaging, licence) against OpenMS's existing Param parser; defer `$..._INSTRUMENT_DIR`, user config dir and `-instrument_file` until a user asks (B4). |
| 3 | Which instruments get a file | **Astral + timsTOF files, but keep `instrumentClass` as the fallback resolver** (Orbitrap family 9, any-TOF 4, unknown 6) instead of generic 6. Byte-identical to 0.2.15 for every instrument, still delivers extensibility. If files-only is chosen anyway: a `WARNING:` whenever the resolved multiple differs from the legacy class rule, plus a CHANGELOG entry — never silent (B1). |
| 4 | RT window in `default.yaml` | **Yes.** Cite the source of 7 and 2 in the file; decide whether a user's replacement `default.yaml` must be complete (B3). |
| 5 | One-line unknown-option message | **Yes to the message; implement it in the patched `TOPPBase::parse_argv`, not as a pre-parse in `main()`.** If the pre-parse survives review, it must consume values of value-taking options (so `-rt_window -1` works), know the flags and `--` variants, and be tested for exactly those (D1/D2). |
| 6 | Diagnostics behind `-debug 1` | **Yes**, plus: grep tests and CI (not just benchmark scripts) for the moved lines in the same commit, and ship `docs/messages-review.md` (E1). |
| 7 | Release 0.2.16 now, cleanup as 0.3.0 | **0.2.16 now: yes — but fold decision 1's aliases into it**, or the alias period is zero releases long. The cleanup as 0.3.0 then removes them (or 0.4, if 1 slips). Note in the 0.2.16 CHANGELOG, in plain words, that results change vs 0.2.15 (RT window, decoys, threads) — that release is not result-compatible regardless of this cleanup (A1, A3). |

The two items I would not implement without owner sign-off: decision 3's fallback rule (silent 9→6 regression) and the alias/release sequencing. Everything else is spec-gap fixing within the proposal's own shape.
